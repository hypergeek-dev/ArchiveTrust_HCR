# ArchiveTrust Telemetry Standard v1: PROV-O and OpenLineage Mapping

**Status:** Mapping guidance, not an implemented exporter.  
**Date:** 16 July 2026  
**Profile:** `archivetrust.telemetry.standard.v1`

## 1. Purpose

This document explains how ArchiveTrust's telemetry concepts relate to W3C PROV-O and OpenLineage
so external adopters can understand the overlap before building exporters.

The mapping is intentionally conservative:

- PROV-O is the better fit for fine-grained evidence, observation, derivation, and responsibility.
- OpenLineage is the better fit for run/job/dataset lineage and operational integration.
- ArchiveTrust-specific decision rationale and epistemic review facts should remain extension
  facets/properties rather than being flattened into generic lineage edges.

## 2. PROV-O Mapping

PROV-O models provenance around entities, activities, agents, and relationships such as generation,
usage, derivation, association, and attribution.

Recommended mapping:

| ArchiveTrust concept | PROV-O concept | Notes |
|---|---|---|
| Archive object | `prov:Entity` | Immutable source entity. |
| Evidence | `prov:Entity` | Generated from provider activity; content-addressed. |
| Observation | `prov:Entity` | Derived from Evidence. |
| CanonicalObservation | `prov:Entity` | Generated by comparison/reconciliation activity. |
| CanonicalDocument | `prov:Entity` | Generated by canonical document assembly activity. |
| Provider invocation | `prov:Activity` | Uses archive object, generates Evidence/Observation records or rejection facts. |
| Alignment/comparison | `prov:Activity` | Uses Observations, generates comparison/canonical decision facts. |
| Human review decision | `prov:Activity` | Uses a ReviewPacket and CanonicalObservation, generates correction/outcome facts. |
| Reviewer/provider/system | `prov:Agent` | Responsible party or software component. |
| `EvidenceCreated` | `prov:wasGeneratedBy` | Evidence generated by provider invocation. |
| `ObservationCreated` | `prov:wasDerivedFrom` | Observation derived from Evidence. |
| `CanonicalDecisionCreated` | `prov:wasGeneratedBy` + `prov:used` | Canonical observation generated by reconciliation using Observations. |
| `HumanCorrectionApplied` | `prov:wasRevisionOf` | Superseding canonical observation revises prior one. |
| `ReviewPacketDispatched` | `prov:Activity` or qualified usage | Packet lifecycle activity begins. |
| `ReviewPacketClosed` | activity end metadata | Closure kind remains ArchiveTrust-specific. |

ArchiveTrust fields that should become PROV attributes rather than core relationships:

- policy version fields;
- `basis_code`;
- `review_intent`;
- `closure_kind`;
- provider failure details;
- integrity verification status.

## 3. OpenLineage Mapping

OpenLineage models lineage around run events for jobs, with input/output datasets and extensible
facets.

Recommended mapping:

| ArchiveTrust concept | OpenLineage concept | Notes |
|---|---|---|
| One document processing run | Run | The run id can be `ProvenanceContextEstablished.context_id` when present. |
| Provider invocation or full pipeline | Job | Choose granularity per exporter; full pipeline is simpler for v1. |
| Archive object | Input Dataset | Dataset type `FILE` where supported. |
| Telemetry stream | Output Dataset | Append-only event log artifact. |
| Canonical JSON export | Output Dataset | A3 export artifact. |
| Provider/runtime metadata | Run/Job facets | Provider id/version, git commit, policy versions. |
| Integrity sidecar | Dataset facet | Digest/hash-chain metadata as custom facet. |
| Review closure status | Run or custom facet | ArchiveTrust-specific operational quality facet. |

ArchiveTrust should use custom facets for:

- `archiveTrustPolicies`;
- `archiveTrustEvidenceCounts`;
- `archiveTrustReviewClosure`;
- `archiveTrustIntegrity`;
- `archiveTrustReplayCompatibility`.

## 4. Where ArchiveTrust Extends Both Models

ArchiveTrust v1 goes beyond generic lineage in four places:

1. Structured distinction between evidence, observations, canonical observations, and canonical
   documents.
2. Explicit provider no-observation/failure/silence distinction.
3. Decision-rationale records such as alignment, exclusion, comparison, and confidence events.
4. Review packet lifecycle closure separate from review outcome.

Do not erase those distinctions to fit a generic model. Exporters should map the common subset and
carry ArchiveTrust-specific semantics as explicit extension attributes/facets.

## 5. Exporter Guidance

A future exporter should:

- preserve ArchiveTrust ids as stable external ids;
- emit PROV entities for every Evidence, Observation, CanonicalObservation, and CanonicalDocument;
- emit OpenLineage run/job/dataset records at workspace or document-run granularity;
- attach hash-chain/file-digest sidecar data as integrity metadata;
- avoid translating `ReviewOutcomeRecorded` and `ReviewPacketClosed` into the same event;
- document any information loss in the export.

This repository does not yet ship such an exporter. A conforming ArchiveTrust v1 implementation is
not required to emit PROV-O or OpenLineage.
